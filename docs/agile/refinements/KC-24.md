**Security blockers**

- **B-1 — unsatisfiable as written.** Security requires CODEOWNERS on `.github/**` *with
  code-owner review required*, so a PR cannot weaken its own lint. A code-owner review is
  an approval: with you as the only owner, GitHub blocks your own PRs. B-1 holds only with
  Q1(b) (bot account) or if it is replaced by a required check that fails when
  `.github/**` changes without a `po:guardrail-change` label (fits Q1(a)).
- B-2 to B-6 have an agreed design (§ Security): read-only token and no
  `pull_request_target`; untrusted input passed through `env:`; zero-dependency lint or
  SHA-pinned actions; no bypass (subject to Q2); checks fail, never warn.

## Outcome

Every commit that reaches `develop` or `main` names the backlog item it serves, and no
change reaches them without the three keys — so "which commit delivered KC-n, and who
checked it?" is answered by `git log --grep "Refs: KC-n"` and the PR record, not by memory.

## Money and trust risks

No money moves. Indirectly: an unreviewed change to `Ledger` or a funds hold can reach
`main` with no traceable item and no proof of review — and an auditor asking "who approved
this change to cash-out?" gets no answer. A force-push can rewrite the evidence behind the
keys. Over-strict rules are a risk too: a guardrail people bypass is worse than none, and a
hotfix to a wrong balance must not be stuck behind a lint (business). Whether change-approval
evidence is required for an e-money issuer is *to confirm with compliance*.

## Design — backend

- **Where it lands**: repository tooling, outside `auth`, `payment` and `shared`; no
  `src/main` change, no migration, no layer or coupling moved.
- **Files**: `.github/workflows/git-flow.yml` (one workflow, never path-filtered,
  `pull_request` into `develop` and `main`); `.github/scripts/lint-commits.sh` (also
  runnable locally); `.github/pull_request_template.md`;
  `.github/rulesets/protected-branches.json` (reviewable record of the applied ruleset).
- **branch-name job**: `^(feature|hotfix)/KC-[0-9]+-[a-z0-9-]+$` and
  `^release/(api|mobile)-v[0-9]+\.[0-9]+$`; `feature/*` → `develop` only; `hotfix/*` and
  `release/*` → `main` or `develop`.
- **commit-lint job**: `fetch-depth: 0`, `git log --no-merges base..head`; subject
  `^(feat|fix|refactor|test|docs|perf|chore|adr)\([a-z]+\)!?: .+`, trailer
  `^Refs: KC-[0-9]+$`; merge commits excluded; shell rather than npm commitlint (no Node,
  no extra dependency to scan under D-19).
- **three-keys job** (if Q1(a)): reads PR labels from the event payload, no API call;
  passes on `po:accepted` with (`checker:pass` and `qa:accepted`) or `po:override`;
  re-runs on `labeled` / `unlabeled`.
- **Settings / ruleset, both branches**: merge commits only; PR required, 0 approvals;
  the checks above required; conversations resolved; no force-push, no deletion. Applied by
  hand in the GitHub UI after the first story merges — no `gh` locally.
- **Developer tests**: `lint-commits.sh` run locally on a valid message, a retired-format
  one, one without `Refs:`, a merge commit; then throwaway PRs recording each refusal.
  No JUnit: nothing under `src/`.
- **ADR**: yes, ADR-010 — required approving reviews rejected (self-approval impossible),
  three keys as labels plus a required check chosen. Subject to Q1.

- Constraints on this item: the branch check accepts `release/mobile-v<major>.<minor>`,

## Security and compliance

- **Exposure: material** — no money or PII, but third-party CI code, a token privilege,
  and a change to who may change `main`.
- **Threats and controls**:

| Threat (STRIDE) | Actor and abuse | Impact | Control | Blocker? |
|---|---|---|---|---|
| Tampering / Elevation | fork PR under `pull_request_target`, or checkout of the head with a write token | write token, push to `develop` | `pull_request` only; `permissions: contents: read`; repository default token read-only; approval for outside contributors' workflows | B-2 |
| Elevation | branch name or PR title interpolated into `run:` | code execution on the runner | pass untrusted input only through `env:`, quoted | B-3 |
| Tampering | the PR rewrites the lint to always pass | guardrail voided | CODEOWNERS on `.github/**` with code-owner review — see B-1 | B-1 |
| Tampering | an action tag moved to malicious code | supply chain | zero-dependency shell lint, actions pinned by full SHA | B-4 |
| Repudiation | Claude commits under Joël's identity | maker and checker indistinguishable | bot identity or mandatory trailer — disagreement D1 | — |
| Elevation | the sole admin bypasses, force-pushes, merges without keys | keys meaningless | empty bypass list, enforced on admins (Q2) | B-5 |

- **PII and redaction**: the repository is public, so PR evidence is public; the template
  says synthetic data only.
- **Audit evidence**: commits with `Refs:` kept by no-squash; checker verdict, `/accept`
  record, PO acceptance; override reasons in `review.md`; the ruleset JSON under `.github/`
  changed in the same PR as any settings change; GitHub's security log.
- **Compliance — to confirm**: BEAC and BCEAO e-money frameworks are expected to require
  change management and segregation of duties for issuers' systems; the three keys under
  protection would be the evidence. No AML/CFT, card-scheme or data-protection impact
  beyond the public-evidence point.
